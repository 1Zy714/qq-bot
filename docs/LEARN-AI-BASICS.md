# AI 基础知识：用这个项目建立直觉

> 目标：不是为了做题，而是**能看懂、能解释、能面试**。
> 每个概念都对应项目里的真实代码，学完能指着代码说「这就是 XX」。

---

## 0. 先破除三个误解

| 误解 | 实际 |
|---|---|
| 「AI 会思考」 | 它做的是**下一个 token 的概率预测**；所谓推理，是很好的副产品 |
| 「上下文越长越好」 | 上下文有上限、要花钱、会稀释重点；项目里大量工作在**控制注入什么** |
| 「温度高 = 更聪明」 | 温度只改变随机性；调高更发散，不等于更对 |

---

## 1. 概念地图

| 概念 | 一句话 | 项目里在哪 |
|---|---|---|
| **token** | 模型处理的最小单位，中文约 1 字 ≈ 1~2 token | 所有 `max_tokens` 配置 |
| **上下文（context）** | 模型这次能看到的全部输入，有长度上限 | `max_prompt_chars`、32k 窗口 |
| **温度 / top_p** | 采样随机性；0 最确定 | `temperature` 配置 |
| **量化（quantization）** | 把权重压成更低精度，省显存、略降质量 | Strata 的 `iq2_xs` |
| **提示词工程** | 用 system/user 组织指令与数据 | `official_bot.py:1214` |
| **前缀缓存** | 相同前缀不重算，省时间 | [CHAT-PERF.md](CHAT-PERF.md) |
| **工具调用（function calling）** | 模型输出「我要调哪个函数、参数是什么」 | `tools/nagi_mcp.py` |
| **MCP** | 一套标准的「工具接口协议」（stdio JSON-RPC） | `mcp_bridge.py` |
| **RAG / 检索增强** | 先去库里找相关片段，再让模型回答 | `memory_search.py` |
| **Agent 循环** | 观察 → 决策 → 动作 → 再观察 | `game_loop.py:193` |
| **幻觉** | 模型编造看似合理的内容 | 项目用「核验」对抗（`game_loop.py:308`） |

## 2. 一个请求到底发生了什么

```
你的话 → 拼 system（人设+记忆摘要）→ 拼历史 → 调模型
       → 模型逐个产 token → 返回文本（可能带工具调用）
       → 摘标记 → 清洗 → 发送
```

对应代码：`official_bot.py:1214` 的 `Responder.answer`。

**关键洞察**：模型本身不记任何东西。所谓「记忆」，是每次把相关内容**重新塞进上下文**。

---

## 3. 提示词分层：system / user / assistant

| 角色 | 放什么 | 项目的做法 |
|---|---|---|
| system | 人设、规则、长期摘要 | **逐字稳定**（为了前缀缓存） |
| user | 用户这句话 + 本轮动态信息 | 标签、检索结果、时间都塞这里 |
| assistant | 模型之前的回复 | 历史追加 |

为什么动态内容放 user？看 [CHAT-PERF.md](CHAT-PERF.md)：system 一变，缓存全废，回复从 0.2s 变 1.3s。

---

## 4. 上下文与前缀缓存

- 模型每次推理都要「读」完整上下文，越长越慢越贵。
- llama.cpp 会缓存**相同前缀**的计算结果；所以项目把 system 固定、历史只追加。
- 这也是为什么「记忆摘要」要刻意保持稳定（按 uid 排序、不含时间戳）。

**练习**：打开 `user_memory.py` 的 `digest`，看看它为什么不用时间戳。

---

## 5. 本地推理与显存（16GB 的取舍）

| 事实 | 项目里的表现 |
|---|---|
| 模型越大越吃显存 | 27B 量化模型约占 13.4GB |
| 上下文也吃显存 | 32k 上下文有额外 KV 缓存 |
| 同时开多个模型会 OOM | 本地模型 + 游戏会挤爆 16GB |
| 量化换显存 | `iq2_xs` 量化让它能塞进消费级显卡 |

**结论**：本地部署不是「越大越好」，是「在显存预算里选够用的」。

## 6. 工具调用与 MCP

模型不会自己发 HTTP 请求。做法是：

1. 给模型一份**工具清单**（名字、参数、说明）
2. 模型输出结构化调用（JSON）
3. 宿主执行，把结果作为新的消息喂回去
4. 模型继续生成

项目里的 `tools/nagi_mcp.py` 就是把星露谷的 HTTP 接口包成 MCP 工具（`call_tool` 135、`handle` 209）；
`mcp_bridge.py` 是客户端（`init_servers` 199），还带健康检查门控（`health_ok` 34）。

## 7. Agent 循环：从「会说」到「会做」

`game_loop.py:193` 的 `_tick` 是标准 Agent 循环：

```
预算检查 → 观察（读游戏状态）→ 候选动作 → 执行 → 核验 → 记账
```

关键设计（面试可讲）：

- **动作要核验**（`_verify_tile` 308）：不信「我完成了」，回去看数据变没变
- **预算**（`_budget_reason` 242）：动作/模型调用/时长任一超限就收工
- **失败记忆**：同一格失败两次就跳过，避免死循环

---

## 8. 记忆与 RAG：不用向量也能做

很多教程说「RAG 必须上 embedding + 向量库」。项目里采用的是更朴素的方案：

| 步骤 | 做法 | 文件 |
|---|---|---|
| 存储 | 结构化事实（人物档案 / 成长记录） | `user_memory.py`、`growth_log.py` |
| 写入 | 合并去重（事实键/子串/前缀） | `add_notes` |
| 检索 | 关键词（中文二元组）+ 30 天时间衰减 | `memory_search.py:197` |
| 注入 | 只给命中前几条，≤600 字 | `digest` 223 |

**什么时候该上向量**：库大（>几千条）、同义表达多、需要语义相似。像「记得谁爱喝什么」这种，关键词足够。

## 9. 多会话与人格

- 会话键：`group:<id>` / `c2c:<openid>`，不同会话历史互不相通。
- 人设：system 里的一段长提示词，决定「怎么说话」。
- 人格切换：`PersonaStore` 存文件、支持聊天内切换。

---

## 10. 怎么判断「变好了」

别只看感觉，看三个数：

1. **延迟**：`[qq] ... 用时 x.xs`
2. **成功率**：错误日志条数 / 总请求
3. **核验率**：动作上报成功但现场没变的次数（`[game] 失败：上报成功但未核验`）

---

## 11. 常见误区（面试踩坑点）

1. 「上下文窗口大 = 记得多」→ 记得多但会稀释重点，且贵。
2. 「温度 0 = 一定正确」→ 只是更确定，不是更对。
3. 「模型说完成了 = 完成了」→ 必须外部核验。
4. 「上向量库 = 高级」→ 数据量小、查询简单时是过度设计。
5. 「本地模型 = 免费」→ 显存、电费、维护都是成本。
6. 「提示词越长越好」→ 关键是指令清晰、顺序合理。
7. 「微调能解决一切」→ 多数场景 RAG + 提示词更便宜。
8. 「模型会记住上次对话」→ 不会，全靠你把历史塞回去。

## 13. 面试常问（附答题要点）

1. **你怎么理解 LLM 的「记忆」？**
   → 模型无状态；记忆 = 每次把相关片段重新拼进上下文；项目用「档案 + 按需检索」控制注入量。
2. **为什么控制 system 稳定？**
   → 前缀缓存；变了就全量重算，延迟从 0.2s 到 1.3s。
3. **工具调用怎么实现？**
   → 工具清单 + 结构化输出 + 宿主执行 + 结果回填；MCP 是标准化的那层。
4. **Agent 怎么防止乱来？**
   → 预算 + 动作核验 + 失败记忆（项目里都有）。
5. **RAG 和微调怎么选？**
   → 知识频繁变、要引用来源 → RAG；风格/格式固定、数据足 → 微调。
6. **怎么评估效果？**
   → 延迟、成功率、核验率；有日志才谈得上优化。
