# QQ 机器人记忆实现：现状、业界做法与建议（2026-10-27）

> 触发：主人要求「查查更好的机器人记忆实现逻辑」。
> 结论放前面：**不用上 Mem0/Zep 那套全家桶**；抄「事实去重 + 按需检索 + 衰减遗忘」
> 三件事就够，其中第一件今天已经做了。

---

## 一、现在的记忆有几层

| 层 | 文件 | 机制 | 注入方式 |
|---|---|---|---|
| 人物档案 | `user_memory.py` → `memory/users.json` | 按 openid 记昵称/次数/`[记住:…]` 印象 | 拼进 system 后缀（刻意保持稳定，保前缀缓存） |
| 跨会话 | `cross_session.py` | 内存里按会话留 14 条、30 分钟 | 读时现算，拼进 user 消息 |
| 成长附录 | `growth_log.py` | 只追加 JSONL + 哈希链 | 最近 6 条进 system |
| DSH 侧 | `.dsh-qq-home` | **没有**（mnemon 只装在 web profile） | — |

## 二、现在的问题

1. **只能按关键词/名字命中**，没有真正的检索（问「上次那个 bug 怎么修的」找不到）
2. **同一事实会并存多版本**（「住在北京」「住在杭州」都在）——今天已修
3. **只增不减**：没有衰减/遗忘，档案和成长会越滚越大
4. **没有离线整理**：没人做合并、摘要、反思
5. 跨会话窗口只有 30 分钟，超出就忘

## 三、业界方案（2026 主流）

| 框架 | 核心思想 | 适合 |
|---|---|---|
| **Mem0**（★38K） | 每条消息用**小模型抽成 typed fact**，再做 ADD/UPDATE/DELETE 去重；向量 + 图检索 | SaaS bot，默认选择 |
| **Zep**（★12K） | 记忆是**时间线**：每条消息是事实或摘要，图 + 向量检索 | 客服/聊天密集型 |
| **Letta（MemGPT）**（★17K） | 记忆是**虚拟上下文**，agent 自己读写内存块 + 摘要树 | agent 需要推理自己的记忆时 |
| **LangMem**（★3K） | LangGraph 原生 store + retrieve | 已在 LangGraph 上 |

共同点：**抽取成结构化事实**、**去重/更新**、**按需检索**、**遗忘**。
对个人 bot 来说，前三家里任何一家的整套都太重（要向量库/抽取模型/额外服务）。

## 四、现成的 QQ 侧方案

### Aegink/dsh-channel-qq（★3，2026-10-25）

DSH 的 QQ 渠道插件（OneBot v11 / SnowLuma），记忆这块设计最值得抄：

```
日记（原始流水）→ 结构化记录（抽取）→ 检索
夜间九任务：分块 / 抽取 / 反思 / 遗忘 / 摘要 / 向量重建
每回合注入 3–8 条证据（≤600 字）；qq_memory_search 深召回原文块（带文件行号）
可选向量：本机 embed 服务；不开就退回关键词
```

**局限**：走 OneBot（SnowLuma/NapCat），不是官方平台路径，不能直接用在主人的
官方 bot 上；但「日记→结构化→检索 + 夜间整理」这套流程可以照搬。

### dsh-mnemon（★724）

分层记忆（工作记忆 / 文档 / 记忆空间）+ 多种 provider（mem0 / honcho / hindsight /
supermemory…）+ 自进化技能。已装在 web profile，**没装进机器人的 sdk home**。
能用，但每回合注入会加延迟，且需要 provider 端点。

### dsh-fish-memory（★253）

会淡忘的记忆：**半衰期 30 天**、每天最多记 8 条、**事实键只留最新**。
「事实键只留最新」正是今天抄进 `user_memory.py` 的那条。

## 五、建议路线

### P0（已做，本次提交）

`user_memory.add_notes` 现在会合并而不是无脑追加：

| 规则 | 例子 |
|---|---|
| 精确重复 → 跳过 | 「爱喝茶」再加一次不增加 |
| 带事实键且同键 → 用新值替换 | 「住在：北京」→「住在：杭州」 |
| 互为子串 → 留更具体 | 旧的被新的包含时替换 |
| 共同前缀够长（≥4 字且 ≥60%）→ 视为同一件事，留更具体的 | 「养了一只猫」→「养了一只橘猫叫咪咪」 |

效果：档案不再无限膨胀，喂给模型的 digest 更准、更短。单测覆盖 9 个场景。

### P1（建议下一步，约 1 天）

**按需检索**而不是全量注入：

- 把 `users.json` 的 notes、`growth.jsonl`、每日对话日记切成块
- 没有 embed 服务就先用「关键词 + 时间衰减」打分（本地模型 32k 上下文够用）
- 模型用 `[回忆:关键词]` 标记触发，像 `[记住:]` 一样解析，**不引入工具调用**（保延迟）
- 命中后注入 ≤600 字证据（带时间），只给需要的这一轮

### P2（1–2 天）

**衰减与整理**：

- 半衰期（30 天权重减半），超期自动降权/删除
- 夜间（游戏循环 idle 时）跑一次：合并重复、把多条印象压成一句摘要、重建索引
- 记录「反思」：从最近对话里抽一条「我学到什么」进成长附录（已有哈希链）

### P3（可选）

如果希望 DSH 侧也带记忆（跨 QQ 与网页），把 `dsh-mnemon` 装进
`.dsh-qq-home` 的 sdk profile 并建一个 Memory Space（mnemon CLI 已装 0.2.12）。
代价：注入变长、延迟上升；建议先在 P1/P2 做完后评估。

## 六、避坑

1. **别叠加多个记忆插件**：maid 自带轻量记忆，再装 fish-memory/mnemon 会重复注入。
2. **system 注入必须稳定**：动态内容（时间戳、最近条数）放 user 消息里，否则前缀缓存全废。
3. **成长附录只追加**：要「修正看法」就再写一条，不要改历史（哈希链会断）。
4. **隐私**：私聊内容只按点名放开（见 `cross_session.py` 的保守规则）。
