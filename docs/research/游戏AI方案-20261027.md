## 二、四种实现架构

所有方案都是这四层，区别只在谁写、哪层现成：

```
① 身体         ② 协议            ③ 大脑                ④ 入口
SMAPI Mod  →  MCP/HTTP/CLI  →  DSH 插件 / 自研循环  →  QQ 机器人 / 游戏内聊天
```

### A. 主人现状（已在跑，最接近能用）

```
QQ 官方 bot ─SDK─> DSH sdk profile ─MCP─> StardewValley-MCP ─文件桥─> SMAPI Mod
                                    └─ game_loop.py（动态候选 / 失败记忆）
```

- 身体：amarisaster 的 mod（主人本地改过：`move_player`、`player_use_tool`、碰撞检测）
- 25 个 MCP 工具，**Windows 实机验证过**
- 缺点：MCP 通道只有「全局 13 + player 12」，商店/节日/小游戏没暴露；文件桥有延迟和并发写风险（分屏那个坑）

### B. 换身体：NagiBridge（HTTP）

```
QQ bot / DSH ─HTTP─> NagiBridge (:7842) ─直接调用─> 游戏
```

- 单 DLL 进 `Mods/`，**不用编译**，官方 Release
- 端点覆盖：状态、移动、寻路、工具、交互、导航、商店、菜单/制作/机器、动物、节日、小游戏、游戏内聊天
- 自带游戏内聊天：API 模式（**任意 OpenAI 兼容端点，可直接指本地 Strata 8080**）或 Channel 模式（Claude Code）
- 缺点：**没有 MCP**，要接 DSH 得写一层薄封装（把 HTTP 包成 MCP 或直接让 game_loop 调）

### C. 全栈框架：ai-native-game-harness

```
玩家/QQ ─DSH 插件─> Adapter ─桥─> Mod（星露谷 / 饥荒 / 缺氧）
```

- DSH 插件承载：Agent、视觉、ASR、TTS、记忆、会话隔离、工作编排
- Windows 是主要开发平台；三款游戏共用一个接入协议
- 缺点：`1.2.0-dev.0`，**开发验证阶段**，安装器/验收未完成

### D. 自主游玩：agent-stardew

```
DSH 插件（Jev 控制器 + 运行面板 + skill）─WS─> CLI ─> SMAPI Mod
          └─ OpenRouter ~typesafe/jev-latest（专用决策模型）
```

- 设计最值钱：动态候选、单步/暂停/停止、**结果核验**（`cropId/cropCount/watered`）、预算（100 次调用 / 15 分钟）、阶段规划回传
- 缺点：**必须 OpenRouter Key**（决策模型在云上，和「本地模型」目标冲突）；编译基线 macOS + SV 1.6.15 + SMAPI 4.5.2，Windows 未验证；开发版

## 四、推荐路线（按性价比排序）

### 路线 1：NagiBridge 当「第二身体」，先只读对比（1 小时）

```powershell
# Windows：下载 NagiBridge.zip → 解压到 Stardew Valley/Mods/
# 启动游戏后：
curl http://localhost:7842/state
```

- 只读 `/state` 和 `/status`，跟现有 MCP 的 `get_state` 对一遍
- 看商店/节日/小游戏这些现有 MCP **没有**的端点值不值得换
- 风险最低：不改现有链路

### 路线 2：把 NagiBridge 端点包成 MCP（1-2 天）

- 写一个 200 行的 MCP server，把 `/state` `/move` `/tool` `/interact` 等映射成工具
- 机器人侧几乎零改动（还是走 MCP），立刻多出商店/节日/小游戏能力
- 顺带解决文件桥的并发问题（HTTP 请求-响应，无共享文件）

### 路线 3：抄 agent-stardew 的「核验 + 预算」设计，不抄它的模型（2-3 天）

- 现在的 `game_loop.py` 已有动态候选和失败记忆，缺的是：
  - **完成条件核验**（不是模型自称完成，而是查 `cropId/cropCount/watered`）
  - **调用预算**（100 次 / 15 分钟，防止死循环烧时间）
  - **阶段回传**（阶段结果 + 受阻证据回到会话）
- 这三样不依赖它的 OpenRouter，本地模型也能跑

### 路线 4：QQ 侧通用接法（如果以后装 DSH 游戏插件）

把游戏插件装进机器人自己的 sdk home，QQ 消息就能直接触发游戏工具：

```bash
DSH_HOME=~/qq-bot/.dsh-qq-home \
  ~/.local/bin/pnpm10 ... plugin --profile sdk add <游戏插件>
```

（`plugin_manager` 工具也能装 bundle；改完要重启 bot）

### 路线 5（观望）：ai-native-game-harness

- 体系最完整（NPC 对话 + 语音 + 工作编排 + 三款游戏）
- 但 `1.2.0-dev.0`，建议等它出稳定版再评估
- 它的 adapter 协议（`protocol/v1`）值得先读，将来复用

## 五、风险与注意

| 风险 | 说明 |
|---|---|
| 存档 | 任何"换身体"操作前先备份存档；agent-stardew 提到用自己的测试存档 |
| 安全 | NagiBridge 有 `/cheat` 类端点——QQ 群里谁都能下指令时，必须加管理员闸（参考 `qq-admin-relay`） |
| 并发 | 分屏/双开时 HTTP 也会共享端口，NagiBridge 用 7842/7843 区分 host/farmhand，比文件桥好但仍要注意 |
| 云依赖 | agent-stardew 的 Jev 在 OpenRouter 上；主人目标是本地模型，别混 |
| 版本 | agent-stardew 验证的是 dsh `0.1.5-rc.1`，本机是 `0.2.1-rc.3`，插件接口可能不兼容 |

## 七、NagiBridge 实机对照（2026-10-27 晚，已在主人机器上跑通）

装法：Release 的 `NagiBridge.zip` → 解压到 `Mods/`（SMAPI 4.5.2 / SV 1.6.15 满足
`MinimumApiVersion 4.0.0`），用 SMAPI 启动游戏后日志出现
`NagiBridge HTTP server started on port 7842`。

**WSL 访问的坑**：Windows 的 HttpListener 只认 `localhost` 这个 Host，从 WSL
用 `127.0.0.1:7842` 会被回 400 Invalid Hostname。两种写法都行：

```bash
curl http://localhost:7842/status                     # 推荐
curl -H 'Host: localhost:7842' http://127.0.0.1:7842/status
```

### 实测能用的只读端点

| 端点 | 返回 | 实测 |
|---|---|---|
| `/status` | worldReady / 多人标志 | ok, worldReady=true |
| `/state` | 玩家/位置/时间/背包/NPC | 9 个字段，1095B 级 |
| `/surroundings?radius=N` | 格子（含 passable）、NPC、怪物、农夫 | 13 格 / radius=4 |
| `/map` | 建筑、warps、动物 | 247B |
| `/scan` | 全图物体 | 计数 |
| `/menu` | 菜单/商店详情 | 未开菜单时 ok,open=false |
| `/machines` `/animals` `/festival` `/minigame/state` `/chat/history` | 各自详情 | 均可用 |

### 与 MCP 的数据差异

| 维度 | NagiBridge | StardewMCPBridge |
|---|---|---|
| 玩家坐标 | **tile 坐标**（9,9） | 像素坐标（576,608）＝同一位置 |
| 血量/体力/金钱 | ✅ | ✅ |
| 天气 | ❌ | ✅（sunny） |
| 同伴 NPC | ❌ | ✅（companions 数组，当前空） |
| 格子数据 | passable 等（按半径扫） | 由 MCP 工具 `get_surroundings` 现算（含作物/水状态，字段更细） |
| 动作端点 | **40+**：buy/sell/harvest/store/chest/craft/machines/animals/festival/minigame/sleep/wakeup/fishbot/chat/push… | 25 个工具（含 6 种模式、shadow farmer） |
| 通信方式 | HTTP 请求-响应 | 文件桥（每 30 tick 写一次，有并发风险） |

**结论**：NagiBridge 是更好的「手」（动作多、无需编译、无文件竞争、跨平台），
但「同伴 NPC + 天气 + 6 种模式」仍只有 MCP 有。两者可以并行：
Nagi 管动作，MCP 管同伴与天气。下一步若要用 Nagi，写一层 HTTP→MCP 薄封装
即可，机器人侧零改动。

对照脚本：`qq-bot/tools/compare_nagibridge.py`（只调 GET，不碰动作端点）。

## 八、一句话建议

**别换掉现在能跑的东西。** 先在旁边装 NagiBridge 当对照（只读），确认它多出来的端点有用，再考虑包成 MCP 接进来；`agent-stardew` 的「核验 + 预算 + 阶段回传」三件事直接抄进 `game_loop.py`，是投入产出比最高的改造。
